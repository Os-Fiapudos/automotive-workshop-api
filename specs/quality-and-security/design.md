# Design Specification: Verifiable Quality & Security

Satisfies `specs/quality-and-security/requirements.md`. Every section states the
requirement it serves.

## 1. Architecture overview

This feature adds no runtime code. It adds three things around the existing system:

```
scripts/coverage.sh        → measures and enforces RNF06 (BR-Q1, BR-Q2)
scripts/security-scan.sh   → runs the RNF09 scanners locally (BR-Q3)
.github/workflows/ci.yml   → two new jobs: coverage, security
docs/security-report.md    → the mandatory deliverable (BR-Q3..BR-Q6)
internal/handlers_test/sensitive_data_test.go → automated proof of BR-Q7 / RNF08
```

`specs/architecture.md` is **not** modified: no feature slice, no shared package, and no
route changes. `cmd/api/main.go` gains no logic — it is touched only by the two SAST fixes
in §6 (explicit server timeouts and a logged encode error), which change no route, no
dependency wiring, and no response body.

Two new directories appear at the repository root: `scripts/` (executable shell) and, at
runtime only, `coverage/` (git-ignored output). Nothing else moves.

## 2. Coverage measurement — `scripts/coverage.sh` (RNF06, BR-Q1, BR-Q2, AC03, AC05)

### 2.1 Why a script and not a bare `go test` flag

Two properties of this repository force it:

1. **The integration tests live in a separate package.** `internal/handlers_test/` is its
   own package, so by default the statements it exercises in
   `internal/features/service-order/` are credited to nobody. Only `-coverpkg` attributes
   them. Without it, `service-order` reads 26.8% instead of 80.7%.
2. **`-coverpkg` with several packages produces one blended number.** The requirement is
   per-domain ("coverage of the critical domains is ≥80%"), and a blend lets a
   well-covered package hide an uncovered one, so the threshold must be applied per package.

**Revised during implementation (2026-08-24).** This section originally specified one full
`go test` run per gated package. The implementation instead does a single instrumented run
over the whole module (`-coverpkg=./internal/...,./cmd/...`) and aggregates the resulting
profile per package in `awk`, deduplicating blocks — a merged profile repeats each block
once per test binary that instrumented it, and a block counts as covered when any binary
hit it.

The change was made because the two methods were verified to produce identical figures
(service-order 80.7%, product 71.7%, tracking 83.6% by both) while the single run is one
test execution instead of thirteen. Per-package thresholds are still applied
independently, so property 2 above is preserved.

### 2.2 Contract

```bash
scripts/coverage.sh                  # measure, print table, exit non-zero below threshold
COVERAGE_HTML=1 scripts/coverage.sh  # also write coverage/coverage.html
COVERAGE_THRESHOLD=90 scripts/coverage.sh   # override the default of 80
```

Behavior:

- Reads `DATABASE_URL` and `JWT_SECRET` from the environment. If `DATABASE_URL` is unset,
  the script **fails immediately with an explanatory message** rather than measuring — a
  silent measurement over skipped integration tests would report ~25% and, worse, a
  passing-looking number if the threshold were ever lowered. This is the one place in the
  project where a missing `DATABASE_URL` is an error rather than a skip.
- Runs `go test ./... -coverpkg=./internal/...,./cmd/... -coverprofile=coverage/coverage.out`
  once, then aggregates that profile per package (§2.1).
- Prints one aligned row per gated package (`package, coverage, PASS/FAIL`), then every
  other package under a `NOT GATED (informational)` heading, per requirements §3.
- Exits `1` if any gated package is below the threshold, `0` otherwise.

### 2.3 Gated packages

Defined as a single array at the top of the script, so widening the gate later is a
one-line change:

```sh
GATED_PACKAGES="
internal/features/service-order
internal/features/product
internal/features/service-order-tracking
"
```

### 2.4 Output location

`coverage/` at the repository root, added to `.gitignore` (which today only lists `bin/`
and `.env`). Coverage artifacts are never committed — they are regenerated by the command
in the README (AC05) and published as a CI artifact.

## 3. CI pipeline (RNF06, RNF09, AC03, AC06)

`.github/workflows/ci.yml` currently has a single `build` job running `go build`, `go vet`,
and `go test`. That job is **left exactly as it is** — it stays the fast, database-free
signal on every push. Two jobs are added alongside it.

### 3.1 Job `coverage`

```yaml
coverage:
  runs-on: ubuntu-latest
  services:
    postgres:
      image: postgres:16
      env:
        POSTGRES_USER: workshop
        POSTGRES_PASSWORD: workshop
        POSTGRES_DB: automotive_workshop
      ports: ["5432:5432"]
      options: >-
        --health-cmd "pg_isready -U workshop -d automotive_workshop"
        --health-interval 5s --health-timeout 5s --health-retries 10
  steps:
    - uses: actions/checkout@v5
    - uses: actions/setup-go@v6
      with: { go-version: "1.22", cache: false }
    - name: Apply schema and seed
      run: |
        psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f docs/schema.sql
        psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f docs/seed.sql
      env: { DATABASE_URL: "postgres://workshop:workshop@localhost:5432/automotive_workshop?sslmode=disable" }
    - name: Coverage
      run: scripts/coverage.sh
      env:
        DATABASE_URL: "postgres://workshop:workshop@localhost:5432/automotive_workshop?sslmode=disable"
        JWT_SECRET: ci-test-secret
        COVERAGE_HTML: "1"
    - uses: actions/upload-artifact@v4
      if: always()
      with: { name: coverage, path: coverage/ }
```

Three details that are not optional:

- **The seed is a prerequisite, not a convenience.** `docs/seed.sql` inserts the
  administrative user the auth integration tests log in as. Without it,
  `TestLoginWithValidCredentials` fails and the failure cascades through every test that
  needs an authenticated request. This was measured on 2026-08-24 against a clean
  PostgreSQL 16: schema only, 74 failures in `internal/handlers_test/`; schema + seed,
  suite green.
- **`ON_ERROR_STOP=1`** so a broken `schema.sql` fails the job instead of silently producing
  a partial database that then fails as confusing test errors.
- **`if: always()` on the artifact upload**, so a failed threshold still publishes the HTML
  report that explains *why* it failed.

The CI database is created fresh per run, so the schema-drift problem described in §7 does
not affect it.

### 3.2 Job `security`

```yaml
security:
  runs-on: ubuntu-latest
  steps:
    - uses: actions/checkout@v5
    - uses: actions/setup-go@v6
      with: { go-version: "1.25", cache: false }   # scanners only; the module still builds on 1.22
    - run: go run golang.org/x/vuln/cmd/govulncheck@v1.7.0 -format json ./... | tee security/govulncheck.json
    - run: go run github.com/securego/gosec/v2/cmd/gosec@v2.28.0 -no-fail -fmt json -out security/gosec.json -stdout ./...
    - uses: actions/upload-artifact@v4
      if: always()
      with: { name: security-scan, path: security/ }
```

- **Revised during implementation (2026-08-24).** This section originally specified the
  vendors' GitHub Actions (`golang/govulncheck-action`, `securego/gosec`) pinned to release
  tags. The implementation runs both tools through `go run <module>@<version>` instead, in
  CI and locally alike. Three reasons: the module version is the same in both places (the
  actions pin an action, not necessarily the tool inside it), no third-party action enters
  the supply chain, and the version recorded in the report is unambiguously the version
  that ran (BR-Q3).
- **Tool versions are pinned exactly**, never `@latest`: `govulncheck@v1.7.0`,
  `gosec@v2.28.0`, declared once in the workflow's `env` block and mirrored in
  `scripts/security-scan.sh`.
- **The scanner job runs Go 1.25.** Both tools declare `go 1.25` in their own `go.mod` and
  cannot be built by Go 1.22. This affects only the toolchain that builds the scanners; the
  `build` and `coverage` jobs still use the pinned 1.22, and the module's own `go.mod` is
  untouched.
- **`gosec` runs with `-no-fail`.** The first run establishes the baseline the report is
  written from; turning it into a build-breaking gate is a follow-up decision once the
  finding list is known and triaged. `govulncheck` is left failing on findings, since a
  known-vulnerable dependency is unambiguous.
- **Neither tool enters `go.mod`** (BR-Q8). Both actions bring their own toolchain, so
  the module's Go 1.22 ceiling (`CLAUDE.md` §2, §12) is untouched. There is no `tools.go`.

### 3.3 Local equivalent — `scripts/security-scan.sh` (BR-Q2, AC05)

CI-only scanning would make the report irreproducible by a third party. The script runs the
same two tools locally via `go run <module>@<pinned-version>`, writing `security/*.json`
(git-ignored), and prints each tool's version so the report can quote it. The pinned
versions must be verified to build under Go 1.22 — a newer scanner release whose own `go`
directive exceeds 1.22 cannot be used locally and, if that happens, the script pins the
newest release that can and the report notes the discrepancy with the CI action version.

## 4. RNF08 — no sensitive data in logs and error responses (BR-Q7, AC12)

### 4.1 Audit of the current state

Performed on the code as of 2026-08-24; the design's job is to lock this in, not to
discover it late.

- **Log statements**: six call sites (`auth/handler.go:54,77`,
  `service-catalog/handler.go:191`, `httpx/respond.go:24`, `cmd/api/main.go:46,52,131`).
  All log an error value or a port number; none logs a request body, a credential, or a
  token. `auth/handler.go:53` already carries an explicit comment asserting BR5 compliance.
- **Error responses**: every feature maps sentinel errors explicitly and falls through to
  `apierror.Internal("unexpected error")` (or `httpx.Error` for `auth`). A raw driver or
  SQL error is therefore never serialized to the client. The `err.Error()` values that *do*
  reach a response body are domain validation messages from
  `internal/features/*/httpsupport.go` (for example "unit price cannot be negative") — no
  user data, no infrastructure detail.

Conclusion: the code already satisfies RNF08. What is missing is the regression test that
keeps it true.

### 4.2 `internal/handlers_test/sensitive_data_test.go`

A single integration test file, following the existing conventions in that package
(`t.Skip` when `DATABASE_URL` is unset, `testify` assertions, real server via the same
helpers). It drives the error paths that are most likely to leak and asserts on the raw
response body:

| Case | Request | Asserted |
|------|---------|----------|
| Failed login | `POST /auth/login` with a wrong password | body contains neither the submitted password, nor a `$2a$`/`$2b$` bcrypt prefix, nor the user's stored hash |
| Missing token | `GET /auth/me` with no `Authorization` | body contains no JWT (`eyJ` prefix) |
| Expired/invalid token | `GET /auth/me` with a tampered token | body does not echo the submitted token |
| Improper tracking access | `GET /acompanhamento/{code}` with a wrong tracking token | body does not echo the submitted token nor disclose the valid one |
| Internal error path | a request that reaches the `default` branch of a `writeServiceError` | body equals the generic envelope; contains no `postgres://`, no `sslmode`, no SQL fragment (`SELECT`, `INSERT`, `pgx`) |

The forbidden-substring list lives in one slice constant so the same assertion helper covers
every case and new cases are cheap to add.

This is the only new test the ticket's scenario list actually requires (requirements §5,
row 10).

## 5. Closing the product coverage gap (RNF06, AC03)

`internal/features/product` is at 71.7% and needs ≥80%. The gap is not missing domain
tests — the stock rules are well covered. It is unexercised plumbing. Measured per-function,
the uncovered statements concentrate in:

| Location | Coverage | What is untested |
|----------|----------|------------------|
| `repository.go:108` `FindByCode` | 0.0% | lookup by human-readable code |
| `service.go:91` `GetByCode` | 0.0% | the service path above it |
| `repository.go:284` `IsUsedInQuotesOrOrders` | 0.0% | the guard that blocks deactivating a product in use |
| `repository.go:334` `convertIntToString` | 0.0% | helper reachable only through the above |
| `httpsupport.go:84` `writeServiceError` | 21.4% | most sentinel-error branches never hit through HTTP |
| `model.go:250` `UpdateDetails` | 58.8% | partial-update branches |
| `handler.go` (`getByID`, `deactivate`, `getStockBalance`, `listMovements`) | 55–59% | 404 / invalid-UUID branches |
| `dto.go` `Validate` ×3 | 63–75% | individual validation-failure branches |

Two test additions cover essentially all of it:

1. **`internal/features/product/service_test.go`** (unit, against the existing
   `fakeRepository`): `GetByCode` found/not-found, `UpdateDetails` partial-field
   combinations, deactivation blocked by `ErrProductInUse`, and each `Validate` failure
   branch.
2. **`internal/handlers_test/product_test.go`** (integration, extending the existing file):
   fetch by code, 404 for unknown id and unknown code, malformed UUID, deactivation of a
   product referenced by a quote returning 409 `PRODUCT_IN_USE`, and the error-mapping
   branches of `writeServiceError` reached through real HTTP.

These are ordinary tests for real behavior; none is written to game the metric. If the
measurement lands short of 80% after them, the remaining gap is closed by testing more
behavior — never by narrowing `-coverpkg` or excluding files.

## 6. The deliverable — `docs/security-report.md` (BR-Q3..BR-Q6, AC07..AC11, AC13)

Markdown, versioned in `docs/` beside `entities.md` and `schema.sql`, structured so it can
be exported into the final delivery PDF unchanged.

```
# Vulnerability and Quality Report — automotive-workshop-api

1. Scope and analyzed version      → commit SHA, branch, date, what was and was not analyzed
2. Tools                           → table: tool | version | date | what it analyzes   (BR-Q3)
3. Reproduction                    → the exact commands, runnable by a third party      (AC05)
4. Coverage results                → per-package table, threshold, how it is enforced   (AC03)
5. Findings                        → one subsection per finding                         (BR-Q4)
      ID | Severity | Component | Description | Impact | Recommendation | Status
6. Fixed findings                  → evidence: commit, what changed, how it was verified (BR-Q5)
7. Residual risks                  → accepted findings: justification + residual risk    (BR-Q5)
8. Secrets review                  → what was searched, what was found                   (BR-Q6)
9. Log and error-response review   → method, result, the test that enforces it           (AC12)
10. Conclusion
```

Severity uses CVSS-style bands (Critical/High/Medium/Low/Informational); for dependency
findings the severity reported by the advisory (OSV/GHSA) is used as-is and cited.

### 6.1 Residual risks already identified

These are known before the scan runs and belong in section 7 of the report regardless of
what the tools output. Each is a finding of this analysis, not a task to fix here
(requirements §7):

| Risk | Why it is not fixed here | Residual risk |
|------|--------------------------|---------------|
| No migration tool (`CLAUDE.md` §14) | Adopting one is its own decision | An existing database silently drifts from `docs/schema.sql`, which is all `CREATE TABLE IF NOT EXISTS` and therefore cannot alter an existing table. Observed in practice: a local volume missing `service_order_tracking_tokens` and missing `quotes.version` / `sent_at` / `sent_version` produced 52 integration-test failures. CI is unaffected (fresh database per run); shared environments are not. |
| `sslmode=disable` in local configuration | Correct for local Docker | Must not reach production; documented as a deployment precondition |
| Development credentials in the repository (`admin123` in `docs/openapi.yaml` and the integration tests, `workshop:workshop` in the compose defaults) | They are documented dev-only fixtures, not secrets, and the tests need deterministic credentials | Low, but they must never be reused in a deployed environment. Real secrets stay in `.env`, which is git-ignored. |
| Authorization (roles/permissions, 403) not implemented (`CLAUDE.md` §13) | Out of MVP scope | Any valid token reaches any protected route |
| Customer routes not wrapped in `RequireAuth` (open decision, `CLAUDE.md` §17.2) | Cross-feature behavioral change requiring its own decision | Customer data is reachable without authentication |
| Two competing error envelopes, `httpx` vs `apierror` (open decision, `CLAUDE.md` §17.1) | Migrating `auth` changes its 401/500 response bodies | Inconsistent error contract; no data exposure |
