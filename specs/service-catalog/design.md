# service-catalog — Design

Satisfies [requirements.md](requirements.md). Every section references the requirements it
serves. Decisions marked **[decision]** were approved by the project owner on 2026-08-18
(D1–D4 in `requirements.md`).

## 1. Placement in the architecture

Follows the vertical slice pattern ([specs/architecture.md](../architecture.md)) and reuses
everything the auth feature already introduced — no new cross-cutting package is needed:

- `internal/features/servicecatalog/` — the feature slice: `handler.go`, `service.go`,
  `repository.go`, `model.go`, `doc.go`.
- Reused from `internal/shared/`: `database` (pgx pool), `httpx` (JSON/error envelope,
  RNF04), `middleware.RequireAuth` (FR6/RNF02).
- `cmd/api/main.go` — wiring only: builds the slice and registers its five routes wrapped in
  `RequireAuth`.

**Package naming [decision]**: the directory is `servicecatalog` (spec folder
`service-catalog`), not `service`, because `internal/features/service/` would read as "the
service layer" and collide with the layer vocabulary used in every slice. Inside the package
the domain entity keeps the name from [docs/entities.md](../../docs/entities.md) —
`Service` — so the business layer type is named `Catalog` (`NewCatalog`) instead of the
`Service`/`NewService` used by the auth slice: two types cannot share a name in one package,
and the entity name is the one fixed by the domain documentation.

No new external dependency (CLAUDE.md §12): `pgconn`, used to identify a unique-violation,
ships inside the already-pinned `github.com/jackc/pgx/v5` module.

## 2. Data model (FR1, FR2, FR5; BR1–BR4, BR7)

The `services` table already exists in [docs/schema.sql](../../docs/schema.sql) with
`id`, `code`, `name`, `description`, `price`, `estimated_time`, `created_at`, `updated_at`
and the `CHECK` constraints matching BR3/BR4. Two changes are required:

```sql
-- was: code BIGINT GENERATED ALWAYS AS IDENTITY
code   BIGINT GENERATED BY DEFAULT AS IDENTITY,   -- D1 (BR1, BR2)
-- new column:
active BOOLEAN NOT NULL DEFAULT TRUE,             -- D2 (FR2, FR5, BR6, BR7)
```

- `GENERATED BY DEFAULT` keeps auto-generation when the caller omits the code, while
  allowing an explicit code — which is what makes the uniqueness conflict (409, AC2)
  reachable. The existing `ux_services_code` unique index is what enforces BR2.
  **Known limitation of D1**: explicitly supplied codes do not advance the identity
  sequence, so a later auto-generated code may collide with one inserted by hand and
  surface as a 409 on a request that did not send a code. Documented rather than
  worked around: mixing both styles in the same catalog is a data-entry choice, and the
  response still describes the conflict accurately.
- `active` carries FR2/FR5 and is the flag the future Quote feature will read for BR6.
  Existing rows default to active, so the seed and any pre-existing data stay valid.
- `docs/entities.md` gains the `active` field in the `Service` table; `docs/seed.sql` gains
  one deliberately inactive service so the active/inactive distinction (AC5) has sample
  data.
- New index, in the "frequent workshop queries" section, for the catalog listing filter
  (same rationale as the existing `ix_products_type`):
  `CREATE INDEX IF NOT EXISTS ix_services_active ON services (active);`
- The table is already in the `set_updated_at` trigger array, so updates keep `updated_at`
  fresh with no extra work.

Go model (`model.go`), mirroring the table:

```go
type Service struct {
    ID            string
    Code          int64
    Name          string
    Description   string
    Price         float64
    EstimatedTime *int   // nullable in the schema (BR4)
    Active        bool
    CreatedAt     time.Time
    UpdatedAt     time.Time
}
```

`price` is `NUMERIC(12,2)` in Postgres and `float64` in Go **[decision]**: the project has
no decimal dependency and adding one is not justified by the catalog alone (CLAUDE.md §12).
The database column stays the source of truth for scale/rounding; a future money-typed
representation would be a project-wide change, not a catalog-only one.

## 3. API contract (FR1–FR6; RNF04)

All five routes are **protected** (FR6/RNF02): registered in `main.go` wrapped in
`middleware.RequireAuth`, which answers 401 for a missing/invalid/expired token (AC8).
Every error body is the project envelope `{"error":{"code","message"}}` written through
`shared/httpx` (RNF04).

Service representation returned by every endpoint that returns one:

```json
{
  "id": "d0000000-0000-0000-0000-000000000001",
  "code": 1,
  "name": "Oil Change",
  "description": "Engine oil and filter change.",
  "price": 80.00,
  "estimated_time": 30,
  "active": true,
  "created_at": "2026-08-18T12:00:00Z",
  "updated_at": "2026-08-18T12:00:00Z"
}
```

`estimated_time` is `null` when unset. Field naming is `snake_case`, matching the auth
responses (`access_token`, `token_type`).

### POST `/api/v1/services` (FR1)

```json
{ "code": 1001, "name": "Oil Change", "description": "...", "price": 150.00, "estimated_time": 30 }
```

- `name` required, non-blank after trimming (BR1) — otherwise 400.
- `price` required (absent field ≠ `0`, so the request field is decoded into a pointer) and
  `>= 0` (BR3) — otherwise 400.
- `code` optional (D1); when present it must be `> 0`, since it is the human-readable
  sequential identifier — otherwise 400.
- `estimated_time` optional; when present must be `> 0` (BR4) — otherwise 400.
- `description` optional, defaults to `""` (the column is `NOT NULL`, same convention as
  `service_orders.notes`).
- 201 with the created service (AC1).
- 409 `CODE_ALREADY_EXISTS` when the code collides (AC2, BR2).

### GET `/api/v1/services` (FR2)

- Optional query parameter `active=true|false`; omitted returns every service, active and
  inactive. Any other value is 400.
- 200 `{"items": [ <service>, ... ]}` ordered by `code`. The envelope object (instead of a
  bare array) leaves room for pagination metadata without breaking the contract; pagination
  itself is not specified by the card and is not implemented.
- Every item carries `active`, which is what satisfies AC5.

### GET `/api/v1/services/{id}` (FR3)

- `{id}` must be a UUID; a malformed id is 400 (it never reaches the database).
- 200 with the service, or 404 `SERVICE_NOT_FOUND`.
- An inactive service is still retrievable (AC7).

### PATCH `/api/v1/services/{id}` (FR4)

```json
{ "description": "...", "price": 180.00, "estimated_time": 45 }
```

- Partial update of `name`, `description`, `price`, `estimated_time` (AC6). Absent fields
  are left untouched; a request with no updatable field is 400.
- `code` and `active` are **not** updatable here: the code identifies the service for the
  manager, and activation state is owned by the delete operation. Reactivation is not a
  requirement of this card and is not invented (CLAUDE.md §17).
- A JSON `null` is treated as "field absent" — clearing `estimated_time` back to null is not
  a requirement of the card.
- Same validations as creation (BR3, BR4) → 400; 404 when the service does not exist.
- 200 with the updated service.

### DELETE `/api/v1/services/{id}` (FR5, BR7, D2)

- Always a logical deletion: sets `active = false`, never removes the row (AC7).
- 204 with no body; idempotent (deleting an already-inactive service is still 204).
- 404 when the service does not exist.

### Error codes used

| HTTP | code | Situation |
| --- | --- | --- |
| 400 | `INVALID_REQUEST` | malformed JSON, failed validation, bad id, bad query param |
| 401 | `UNAUTHORIZED` | produced by `middleware.RequireAuth` (FR6) |
| 404 | `SERVICE_NOT_FOUND` | id not present in the catalog |
| 409 | `CODE_ALREADY_EXISTS` | code already used by another service (BR2) |
| 500 | `INTERNAL_ERROR` | unexpected failure; details logged, never returned |

## 4. Layers and flow

Same split the auth slice established (handler = HTTP + error mapping, service = business
rules against small interfaces, repository = SQL, model = data shape):

```
handler: decode + shape validation (400) → Catalog (business rules) → Store (SQL)
```

`service.go` declares the interface it needs, so it stays unit-testable with fakes without
importing `shared` types:

```go
type Store interface {
    Create(ctx context.Context, in NewService) (*Service, error)
    List(ctx context.Context, filter ListFilter) ([]Service, error)
    FindByID(ctx context.Context, id string) (*Service, error)
    Update(ctx context.Context, id string, changes Changes) (*Service, error)
    Deactivate(ctx context.Context, id string) error
}
```

Validation errors are a single type carrying the message shown to the caller:

```go
type ValidationError struct{ Message string }
```

The handler maps it with `errors.As` to 400 `INVALID_REQUEST`, `ErrServiceNotFound` to 404,
`ErrCodeAlreadyExists` to 409, and anything else to 500 (logging the cause, never returning
it) — mirroring `internal/features/auth/handler.go`.

`repository.go` uses plain parameterized `pgx` queries (CLAUDE.md §13):

- `Create` — two statements chosen by whether a code was supplied (one lists the `code`
  column, the other omits it and lets the identity generate), both `RETURNING` the full row.
- `List` — `WHERE active = $1` only when the filter is set; `ORDER BY code`.
- `FindByID` / `Deactivate` — by `id`, `pgx.ErrNoRows` → `ErrServiceNotFound`.
- `Update` — `SET` clause assembled from the fields actually present. Column names come from
  a fixed set inside the repository and values are always bound parameters, so no caller
  input is ever concatenated into SQL.
- A `23505` unique violation (detected via `*pgconn.PgError`) maps to `ErrCodeAlreadyExists`.

## 5. Tests (AC1–AC9)

- `internal/features/servicecatalog/service_test.go` — business rules against a fake
  `Store`: required name, required/negative price (BR3), invalid estimated time (BR4),
  invalid code, empty update, and propagation of not-found/duplicate-code errors.
- `internal/features/servicecatalog/handler_test.go` — status codes and payload shape for
  all five endpoints, including 400 on malformed JSON/id/query param, 409, 404, and the
  500 path that must not leak the underlying error text.
- `internal/handlers_test/servicecatalog_test.go` — integration over real HTTP against the
  compose Postgres, authenticated with a real login token, covering AC1–AC8. It self-skips
  when `DATABASE_URL` is unset, like `auth_test.go`, and cleans up the rows it creates.

Stdlib `testing` only, with hand-written fakes (CLAUDE.md §11).
